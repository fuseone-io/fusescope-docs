**Use this page when** you set the gateway's and the agents' resources, or plan how many gateway
replicas to run. The numbers below were measured; the method is at the
[end of the page](#how-it-was-measured), so you can repeat it with your own telemetry.

<Aside type="danger" title="The default gateway memory limit holds about 10,000 spans/s">
  The chart's default gateway limit is 1Gi. In our measurements, one replica at 20,000 spans/s
  was killed for running out of memory (OOMKilled), and then killed again within seconds of
  each restart while the agents resent what they had buffered. `memory_limiter` did not stop
  it: it watches the Go heap, not the container's memory, and checks once a second. Until the
  chart sets a Go memory limit (`GOMEMLIMIT`), size the limit with the margins below, or run
  more replicas.
</Aside>

## What uses memory

The gateway holds each signal's data for **up to 10 seconds** before one `INSERT` per table:
the service map joins a parent and a child span only within one insert. So the gateway's memory
grows with throughput × 10 s × the in-memory size of a record. That size depends on the number
and length of attributes: the measurements used 8 attributes per record, and records with many
more or much longer attributes need proportionally more.

CPU is rarely the constraint. Memory is.

## Measured: gateway

One gateway replica, one agent, ClickHouse on the same machine. For these runs the gateway's
memory limit was raised to 4Gi (`fusescopeCollector.resources.limits.memory`), so that memory
could be measured past the default. The trace rows up to 10,000 spans/s were measured at the
default 1Gi; all other rows with the 4Gi limit. "RSS" is the peak resident memory
of the process during a 90-second steady window.

|---:|---:|---:|---|
| 2,000 | 0.03 | 442 MiB | none |
| 5,000 | 0.07 | 488 MiB | none |
| 10,000 | 0.13 | 491 MiB | none |
| 20,000 | 0.27 | 983 MiB | none |
| 40,000 | 0.57 | 1,936 MiB | none |
| 60,000 offered | 0.71 | 3,183 MiB | yes: 48,000/s accepted, the rest refused at the agent |

Each point was a gauge with 8 attributes. The points shared few series; many distinct series
add work in ClickHouse, which writes each new series once.

| Points/s | Gateway CPU (cores) | Gateway RSS | Refused |
|---:|---:|---:|---|

| 50,000 | 0.54 | 934 MiB | none |

### Rules of thumb for the gateway

- **CPU:** about **0.015 cores per 1,000 spans/s**, **0.025 per 1,000 log records/s** and
  **0.011 per 1,000 metric points/s**, including TLS from the agents and the ClickHouse inserts.
- **Memory:** a base of about 450 MiB, then about **50 MiB per 1,000 spans/s** above
  10,000 spans/s. Logs need less per record up to 20,000/s, then grow as fast. Metric points are
  the lightest: under 1 GiB at 50,000 points/s.
- **Limit = 1.6 × the expected RSS.** This is an empirical margin, not a guarantee. It leaves
  room for bursts, such as the agents resending after a restart, and for the Go runtime's
  memory beyond the heap. `memory_limiter` refuses data when the Go heap passes 80% of the
  limit, but it does not see the rest of the process's memory and reacts once a second, so it
  cannot by itself keep the container under its limit: the OOM above happened with it on.

## Measured: agents

The agent runs on every node; its load is what that node's pods send to it, plus the node's own
pod logs and metrics when those are on.

| Load on one node | Agent CPU (cores) | Agent RSS | Refused |
|---|---:|---:|---|
| 10,000 spans/s | 0.06 | 124 MiB | none |
| 20,000 spans/s | 0.15 | 181 MiB | none |
| 40,000 spans/s | 0.33 | 162 MiB | none |
| 60,000 spans/s offered | 0.46 | 516 MiB | yes, at the 512Mi default limit |
| 10,000 log records/s | 0.11 | 166 MiB | none |
| 20,000 log records/s | 0.28 | 166 MiB | none |
| 40,000 log records/s | 0.69 | 257 MiB | none |
| 60,000 log records/s offered | | | OOMKilled at the 512Mi default limit |
| 25,000 metric points/s | 0.25 | 211 MiB | none |
| 50,000 metric points/s | 0.55 | 296 MiB | none |
| 100,000 metric points/s offered | | | OOMKilled at the 512Mi default limit |

The default agent resources (100m CPU and 128Mi requested, 512Mi limit) carry up to about
**40,000 spans/s, 40,000 log records/s or 50,000 metric points/s per node**. Few nodes see that much; for those that do,
raise the limit to 1Gi.

## Recommended settings

### Gateway, per replica

| Throughput per replica | CPU request | Memory request | Memory limit |
|---|---:|---:|---:|
| Up to 10,000 spans/s or 15,000 log records/s | 250m | 512Mi | 1Gi (the default) |
| Up to 20,000 spans/s or 30,000 log records/s | 500m | 1Gi | 2Gi |
| Up to 40,000 spans/s or 40,000 log records/s | 1 | 2Gi | 4Gi |

Mixed traffic adds up: 10,000 spans/s plus 10,000 log records/s is roughly the 20,000 row.

```yaml
fusescopeCollector:
  resources:
    requests: {cpu: 500m, memory: 1Gi}
    limits: {memory: 2Gi}
```

### Scale out, not only up

Past about 40,000 spans/s per replica, add replicas instead of memory: each replica holds only
the batches of the connections it serves.

```yaml
fusescopeCollector:
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 6
    targetCPUUtilizationPercentage: 70
    targetMemoryUtilizationPercentage: 70
```

- **Memory utilization is of the request.** Set the memory request to the RSS you expect per
  replica. A 70% target then adds replicas while each one still has the limit's margin above
  it.
- **Two replicas at least**, for restarts and node drains, with a PodDisruptionBudget
  ([Production setup](/collector/production-setup/#gateway)).
- **Load splits by agent, not by record.** Each agent keeps one long-lived gRPC connection to
  the gateway's Service, so a replica serves whole agents. With few nodes, or one node much
  busier than the rest, replicas are unevenly loaded; size each replica for the busiest agents
  it may get. A new replica takes connections only as agents reconnect, for example when they
  restart, so scaling out does not relieve the existing replicas at once.

### Agents

| Busiest node's load | Memory limit |
|---|---:|
| Up to 40,000 spans/s or log records/s, or 50,000 metric points/s | 512Mi (the default) |
| Above that | 1Gi |

```yaml
fusescopeAgent:
  resources:
    requests: {cpu: 100m, memory: 128Mi}
    limits: {memory: 1Gi}
```

Pod logs and kubelet stats add their own load: a node that writes thousands of log lines per
second counts them like OTLP log records.

### ClickHouse

The collector is rarely the bottleneck; ClickHouse often is. In these runs ClickHouse used more
CPU than the gateway, and inserts took 0.1 to 0.5 s on average. When inserts slow down, the
gateway's queue fills, the agents' queues fill, and senders get refusals. Watch
`otelcol_exporter_fusescope_clickhouse_insert_duration` and the queue-backing-up alert before
you add gateway replicas.

## Check your own numbers

From the gateway's own metrics, in FuseScope:

- **Throughput:** the rate of `otelcol_receiver_accepted_spans`, `_log_records` and
  `_metric_points`.
- **Memory:** `otelcol_process_memory_rss`, against the container's limit.
- **CPU:** the rate of `otelcol_process_cpu_seconds`.
- **Refusals:** `otelcol_receiver_refused_*`, which should stay flat.

Divide memory and CPU by throughput to get your own per-record costs, then size with the
1.6 × margin above.

## How it was measured

- **Path:** `telemetrygen` pods → the agent's OTLP receiver (TLS 1.3, bearer token) → the
  gateway's agents' listener (mTLS) → ClickHouse, as in production. For logs and metrics a
  relay in the generator pod sent batches of 512 records to the agent, as SDKs do;
  `telemetrygen` alone sends one record per request.
- **Versions:** chart 0.170.0, which pins collector 0.6.3, with the image overridden to
  collector **0.6.4** (`fusescopeCollector.image.tag: 0.6.4`, `digest:
  sha256:65e3c13edb375a795ea1b3f6e3deba4c37e4326a51e3c0917d308c352800704d`). 0.6.4 changed only
  documentation since 0.6.3, so the results apply to both. One gateway replica, one agent.
- **Machine:** a kind cluster on one AMD Ryzen 9 5950X host (16 cores, 32 threads); the
  generator, the collector and ClickHouse shared it.
- **Load:** each step ran 40 s to warm up, then 90 s measured. CPU is the rate of the process's
  CPU seconds over the window; memory is the peak RSS sampled every 5 s.
- **Records:** traces with 4 child spans per root and 8 attributes; logs with a ~200-byte body
  and 8 attributes; metrics as gauge points with 8 attributes, over few series.

The scripts, configuration and raw results are in the collector's repository, under
[`test/sizing`](https://github.com/fuseone-io/fusescope-collector-server/tree/main/test/sizing).

Your numbers will differ with record size, attribute count, CPU model and ClickHouse speed.
Treat these as a starting point and check them against your own metrics.
