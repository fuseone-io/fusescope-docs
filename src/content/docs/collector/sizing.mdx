**Use this page when** you set the gateway's and the agents' resources, or plan how many gateway
replicas to run. Every number below was measured; the method is at the
[end of the page](#how-it-was-measured), so you can repeat it with your own telemetry.

<Aside type="caution" title="The default gateway sheds excess traces instead of crashing">
  The chart's default gateway limit is 1Gi. In our measurements one replica held 15,000 spans/s.
  At 20,000 spans/s it stayed up, accepted 18,859/s and refused 170/s; at higher offered rates
  backpressure reduced accepted throughput further. These refusals are retryable, but sustained
  traffic above the row still needs a larger limit or more replicas.
</Aside>

## What uses memory

The gateway holds each signal's data for **up to 10 seconds** before one `INSERT` per table:
the service map joins a parent and a child span only within one insert. Its memory grows with
throughput and the size of each record. The chart sets the Go soft memory limit (`GOMEMLIMIT`)
to 80% of the container limit. It configures the collector's `memory_limiter` with
`limit_percentage: 80`, `spike_limit_percentage: 20` and a one-second check interval; under
memory pressure the processor returns retryable refusals instead of letting the pod be
OOM-killed.

For that reason this page gives **the limits at which a replica held or began refusing data**,
not a memory-per-record formula.

CPU is rarely the constraint. Memory is.

restarted pods and ran 90 measured seconds after a 40-second warmup. "Peak RSS" is the highest
resident memory of the gateway process during that window.

## Agents

The agent runs on every node; its load is what that node's pods send it, plus the node's own pod
logs and metrics when those are on. With its **default resources** (100m CPU and 128Mi
requested, 512Mi limit), the agent was never restarted. In individual steps without refusals it
passed up to 80,000 spans/s, 80,000 log records/s or 100,000 metric points/s on its node. Its
peak RSS across all steps was 104 to 422 MiB.

When a gateway was already under memory pressure, backpressure filled the agent's buffers too:
the agent refused data in four rows that also had gateway refusals. Raising the agent limit only
buffers that condition for longer; first add gateway capacity.

| Load on one node | Agent CPU (cores) |
|---|---:|
| 10,000 spans/s | 0.05 |
| 80,000 spans/s | 0.47 |
| 10,000 log records/s | 0.07 |
| 80,000 log records/s | 0.88 |
| 100,000 metric points/s | 0.90 |

Keep the default unless an agent approaches its limit or refuses data while its gateways still
have headroom; then raise its limit to 1Gi.

## Recommended settings

### Gateway, per replica

| Throughput per replica, up to | Memory limit | Memory request | CPU request |
|---|---:|---:|---:|
| 15,000 spans/s, or 30,000 log records/s, or 75,000 metric points/s | 1Gi (the default) | 512Mi | 250m |
| 30,000 spans/s, or 40,000 log records/s | 2Gi | 1Gi | 500m |
| 80,000 spans/s, or 40,000 log records/s, or 100,000 metric points/s | 4Gi | 2Gi | 1 |

- **Mixed traffic adds up.** Add each signal's share of its row: at 1Gi, 7,500 spans/s and
  15,000 log records/s are each half of the row, together the whole row. This is a heuristic, not
  a measurement.
- **The 4Gi log result was not monotonic.** The 60,000/s step had small refusals, while the
  independent 80,000/s step had none. Use 40,000/s as the conservative no-refusal bound until
  you repeat the higher load on your own system.
- **Stay inside the tested range.** The last row is the most we measured on one replica. Past
  it, add replicas instead of memory.
- **CPU** was about 0.009 to 0.011 cores per 1,000 spans/s, 0.012 to 0.018 per 1,000 log
  records/s and 0.009 to 0.012 per 1,000 metric points/s, including TLS from the agents and the
  ClickHouse inserts.

```yaml
fusescopeCollector:
  resources:
    requests: {cpu: 500m, memory: 1Gi}
    limits: {memory: 2Gi}
```

### Scale out, not only up

```yaml
fusescopeCollector:
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 6
    targetCPUUtilizationPercentage: 70
    targetMemoryUtilizationPercentage: 70
```

- **Memory utilization is of the request.** Set the memory request to about half the limit, as
  in the table, so a 70% target adds replicas well before a replica nears its limit.
- **Two replicas at least**, for restarts and node drains, with a PodDisruptionBudget
  ([Production setup](/collector/production-setup/#gateway)).
- **Load splits by agent, not by record.** Each agent keeps one long-lived gRPC connection to
  the gateway's Service, so a replica serves whole agents. With few nodes, or one node much
  busier than the rest, replicas are unevenly loaded; size each replica for the busiest agents
  it may get. A new replica takes connections only as agents reconnect, for example when they
  restart, so scaling out does not relieve the existing replicas at once.

### ClickHouse

The collector is rarely the bottleneck; ClickHouse often is. When inserts slow down, the
gateway's queue fills, then the agents' queues, and senders get refusals. Watch
`otelcol_exporter_fusescope_clickhouse_insert_duration` and the queue-backing-up alert before you
add gateway replicas.

## Check your own numbers

From the gateway's own metrics, in FuseScope:

- **Throughput:** the rate of `otelcol_receiver_accepted_spans`, `_log_records` and
  `_metric_points`.
- **Memory:** `otelcol_process_memory_rss`, against the container's limit.
- **CPU:** the rate of `otelcol_process_cpu_seconds`.
- **Refusals:** `otelcol_receiver_refused_*`, which should stay flat.

To extrapolate from your own peak RSS, start with a limit at about **1.6 × the peak**, then test
your burst size and require zero refusals. This is a planning margin, not a guarantee: record
size, batching, garbage-collection timing and ClickHouse latency all change the peak. Chart
0.171.0 kept every collector process alive in this run, including the steps that crossed the
limiter.

## How it was measured

- **Path:** `telemetrygen` pods → the agent's OTLP receiver (TLS 1.3, bearer token) → the
  gateway's agents' listener (mTLS) → ClickHouse, as in production. For logs and metrics a relay
  in the generator pod sent batches of 512 records to the agent, as SDKs do; `telemetrygen`
  alone sends one record per request.
- **Versions:** chart 0.171.0, which pins collector 0.6.4, with no override. One gateway
  replica, one agent with its default resources. The chart set `GOMEMLIMIT` to 80% of each
  container limit and configured `memory_limiter` with `limit_percentage: 80`,
  `spike_limit_percentage: 20` and `check_interval: 1s`.
- **Independent steps:** before each step the gateway and the agent were restarted, and the step
  began once both were ready and the agent's queues were empty. Each step waited for the
  generator to run, warmed up 40 s, then measured 90 s, sampling every 5 s.
- **Machine:** a kind cluster on one AMD Ryzen 9 5950X host (16 cores, 32 threads); the
  generator, the collectors and ClickHouse shared it.
- **Records:** traces with 4 child spans per root and 8 attributes; logs with a body of about
  200 bytes and 8 attributes; metrics as gauge points with 8 attributes, over few series.

The scripts, every step's raw results and the restart records are in the collector's repository,
under
[`test/sizing`](https://github.com/fuseone-io/fusescope-collector-server/tree/main/test/sizing).

Your numbers will differ with record size, attribute count, CPU model and ClickHouse speed.
Treat these as a starting point and check them against your own metrics.
