A built-in integration is a recipe for one technology, such as PostgreSQL or Nginx. It
gives you an OpenTelemetry Collector config that collects the right metrics and logs, and
FuseScope adds matching dashboards when you connect it.

**Use this page when** you want to monitor a database, web server or AWS service that has
a built-in integration, or want to know how integrations work in the app.

<Aside type="caution" title="Inside the cluster only">
  These configurations are for a collector running as a pod in the Kubernetes cluster that runs
  FuseScope: the exporter sends to the FuseScope agent's Service, which exists only there. A
  collector outside that cluster has no supported destination yet.
</Aside>

## Available integrations

| Integration | Metrics | Logs | Dashboards |
|---|---|---|---|
| [ClickHouse](/sending-data/integrations/clickhouse/) | Server Prometheus endpoint | Server log file | Clickhouse Overview |
| [MongoDB](/sending-data/integrations/mongodb/) | `mongodb` receiver | Server log file | Mongo overview |
| [Nginx](/sending-data/integrations/nginx/) | None | Access and error log files | None |
| [PostgreSQL](/sending-data/integrations/postgresql/) | `postgresql` receiver | Server log file | Postgres overview |
| [Redis](/sending-data/integrations/redis/) | `redis` receiver | Server log file | Redis overview |
| [AWS RDS for MySQL](/sending-data/integrations/aws-rds-mysql/) | CloudWatch and `mysql` receiver | CloudWatch Logs | AWS RDS MySQL, MySQL |
| [AWS RDS for PostgreSQL](/sending-data/integrations/aws-rds-postgresql/) | CloudWatch and `postgresql` receiver | CloudWatch Logs | AWS RDS Postgres, Postgres overview |
| [AWS ElastiCache for Redis](/sending-data/integrations/aws-elasticache-redis/) | CloudWatch and `redis` receiver | CloudWatch Logs | AWS ElastiCache Redis |

No integration ships log pipelines or alert rules. Log parsing happens in the collector
config itself, with `filelog` operators. To parse further, or to parse the raw AWS logs,
add a [log pipeline](/sending-data/log-pipelines/). To get alerted, create
[alert rules](/alerts/alert-rules/) on the collected data.

## How it works

You run the collector. FuseScope does not reach into your systems.

<Steps>

1. **Run a collector in the cluster that runs FuseScope.** Use the upstream `otelcol-contrib`
   distribution, version v0.88.0 or newer; the examples use 0.139.0. See
   [Run the collector](#run-the-collector).
2. **Add the integration's config files.** Each integration page has one file for
   metrics and one for logs. They export to FuseScope over OTLP gRPC.
3. **Connect the integration in FuseScope.** This adds its dashboards and turns on the
   connection test.

</Steps>

## Connect an integration in the app

<Steps>

1. Open **Integrations** in the sidebar and click the integration. Use
   **Search for an integration...** to filter the list.
2. The detail page has three tabs:
   - **Overview**: what the integration collects.
   - **Configure**: the setup steps, the same as on these pages.
   - **Data Collected**: every log attribute and metric, with type, unit and
     description.
3. Click **Connect &lt;name&gt;** in the header, for example **Connect PostgreSQL**.
4. In the **Connect &lt;name&gt;** dialog, click **Show Configuration Steps** to open the
   **Configure** tab, or **I have already configured** once the collector runs.

</Steps>

**I have already configured** installs the integration. Its dashboards appear in
[Dashboards](/dashboards/dashboards/), and the header button becomes
**Test Connection**. A badge shows the status:

| Status | Meaning |
|---|---|
| Listening for data... | Installed, nothing received yet. |
| This integration is working properly | FuseScope has received matching data. |
| This integration has not received data in a while :/ | Nothing received for 7 days. |

**Test Connection** opens a dialog with where the last data came from and when.
FuseScope counts two kinds of data:

- **Logs** that carry the attribute `source` with the integration's value, such as
  `source = postgres`. Every config on these pages sets it. Keep it.
- **Metrics** whose names are listed on the **Data Collected** tab.

To remove an integration, click **Remove from FuseScope** at the bottom of its page,
then **Remove Integration**. This deletes its dashboards and stops the connection test.
It does not change your collector: remove the config there to stop sending data.

## Send to FuseScope

Every config on these pages ends with the same exporter:

```yaml
exporters:
  otlp/fusescope:
    endpoint: ${env:OTLP_DESTINATION_ENDPOINT}
    tls:
      ca_file: /etc/fusescope-agent-ca/ca.crt
    headers:
      Authorization: "Bearer ${env:FUSESCOPE_AGENT_TOKEN}"
```

Set `OTLP_DESTINATION_ENDPOINT` to `fusescope-agent-otlp.fusescope.svc:4317`, the FuseScope
agent on the collector's node, and `FUSESCOPE_AGENT_TOKEN` to the agents' OTLP token. Mount the
agents' CA bundle at `/etc/fusescope-agent-ca`. [OTLP](/sending-data/otlp/) explains how to turn
the agents' receiver on and copy the credentials into your namespace.

<Aside type="tip" title="Already running a collector agent?">
  If a collector on the same host or pod already forwards to FuseScope, point the
  integration's exporter at it instead: `endpoint: localhost:4317` with `insecure: true`, which
  stays on the loopback interface.
</Aside>

## Run the collector

Run the collector as a pod in the cluster that runs FuseScope, for example a Deployment of
`otel/opentelemetry-collector-contrib:0.139.0`. The collector accepts several `--config` flags and
merges the files; put the integration files in a ConfigMap next to your main config:

```yaml title="deployment.yaml (excerpt)"
containers:
  - name: otelcol
    image: otel/opentelemetry-collector-contrib:0.139.0
    args:
      - --config=/etc/otelcol-contrib/postgres-metrics.yaml
    env:
      - name: OTLP_DESTINATION_ENDPOINT
        value: fusescope-agent-otlp.fusescope.svc:4317
      - name: FUSESCOPE_AGENT_TOKEN
        valueFrom:
          secretKeyRef: {name: fusescope-agent-otlp-token, key: token}
      - name: POSTGRESQL_ENDPOINT
        value: db.internal:5432
      - name: POSTGRESQL_USERNAME
        value: monitoring
      - name: POSTGRESQL_PASSWORD
        valueFrom:
          secretKeyRef: {name: postgres-monitoring, key: password}
    volumeMounts:
      - {name: config, mountPath: /etc/otelcol-contrib, readOnly: true}
      - {name: fusescope-agent-ca, mountPath: /etc/fusescope-agent-ca, readOnly: true}
volumes:
  - {name: config, configMap: {name: otelcol-integrations}}
  - {name: fusescope-agent-ca, secret: {secretName: fusescope-agent-ca}}
```

The CA and token Secrets must be in the collector's namespace; see [OTLP](/sending-data/otlp/).
Integrations that read a service's log files need the collector where it can read them, such
as a sidecar sharing the service's log volume.

## Anything else

The integrations cover a handful of common services. The
[collector-contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/receiver)
distribution has receivers for many more, such as Kafka, RabbitMQ, Elasticsearch,
Apache and IIS. Configure the receiver, export with the exporter above, and build a
[dashboard](/dashboards/dashboards/) on the metrics. Services that expose
Prometheus metrics work with the
[Prometheus receiver](/sending-data/prometheus/). For log files, see
[Log files](/sending-data/logs-files/).
