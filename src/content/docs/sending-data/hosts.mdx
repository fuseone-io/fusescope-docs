The **Hosts** tab of [Infrastructure](/observe/infrastructure/#hosts)
lists your machines with their CPU, memory, disk and load. That data comes from the
OpenTelemetry Collector's `hostmetrics` receiver, plus the `resourcedetection` processor, which
names the machine.

**Use this page when** the Hosts tab says **No host metrics yet**, or an
[instrumentation check](/observe/infrastructure/#instrumentation-checks)
reports missing host metrics or `host.name`.

## Kubernetes nodes

The FuseScope agents collect each node's host metrics with `fusescopeAgent.hostMetrics` (on by
default) and name the node with `host.name`. See
[hostmetrics receiver](/sending-data/kubernetes/#hostmetrics-receiver) for what they collect and
what they leave out: without the host network namespace they do not scrape the network or
processes.

## Machines outside the cluster

<Aside type="caution" title="No supported destination outside the cluster yet">
  The FuseScope chart exposes no OTLP endpoint outside the Kubernetes cluster that runs
  FuseScope. A server or VM outside that cluster has nowhere supported to send its host metrics
  yet, so this page has no configuration for it. It will, once FuseScope offers an
  authenticated external endpoint.
</Aside>

## What the Hosts tab needs

| Data | Produced by | Used for |
|---|---|---|
| `system.cpu.time` | `hostmetrics` `cpu` scraper | **CPU usage** and **Iowait** columns |
| `system.memory.usage` | `memory` scraper | **Memory usage** column |
| `system.cpu.load_average.15m` | `load` scraper | **Load avg (15min)** column |
| `system.filesystem.usage` | `filesystem` scraper | **Disk usage** column |
| `host.name` resource attribute | `resourcedetection` processor | One row per host; without it the list is empty |
| `os.type` resource attribute | `resourcedetection` (`system` detector) | **OS Type** filter |

These four metrics and `host.name` are what the instrumentation checks on the Hosts
tab look for.

The host's details panel draws more charts from the same receiver:

| Charts | Metrics | Scraper |
|---|---|---|
| System load average | `system.cpu.load_average.1m`, `.5m`, `.15m` | `load` |
| Disk IO, operations, operation time, queue size | `system.disk.io`, `system.disk.operations`, `system.disk.operation_time`, `system.disk.pending_operations` | `disk` |
| Network usage, packets, errors, drops, connections | `system.network.io`, `system.network.packets`, `system.network.errors`, `system.network.dropped`, `system.network.connections` | `network` |

Process metrics are optional. FuseScope's processes check looks for
`process.cpu.time` and `process.memory.usage` with the `process.pid` resource
attribute, from the `process` scraper. The host panel has no processes view yet;
chart them in [Metrics](/explore/metrics/).

The FuseScope agents run the `cpu`, `memory`, `load` and `filesystem` scrapers only, so for
Kubernetes nodes the disk, network and process charts stay empty.

## Check that it works

1. Open **Infrastructure › Hosts**. A node appears with **Active** status within a few
   collection intervals. Click **Recheck** on the instrumentation checks.
2. If a node is missing but metrics arrive, search for `system.cpu.time` in
   [Metrics](/explore/metrics/) and check that it has `host.name`.
3. Look for errors in the agent's log, such as `failed to read` from a scraper:
   `kubectl -n fusescope logs daemonset/fusescope-agent`.
